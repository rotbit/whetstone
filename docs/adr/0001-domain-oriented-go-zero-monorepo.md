# ADR-0001：采用领域分层的 go-zero Monorepo 与单容器部署

## 状态

Superseded by ADR-0003（部署部分；领域目录决策继续有效）

## 背景

项目需要保留一个统一的 `app-apis` 接入层、三个 zRPC 业务服务以及一个异步报告 Worker。目录应参考 `rec-online-service` 的成熟 Monorepo 组织方式，同时当前阶段希望将所有进程交付在一个容器中，以降低个人项目的部署复杂度。

当前扁平的 `app/app-apis`、`app/user-rpc` 等目录无法直观看出接入层、业务域和后台任务的边界。每个服务独立容器虽然更符合微服务的独立伸缩模型，但会显著增加当前阶段的编排、配置和运维成本。

## 决策

- 接入层放在 `app/apis/cmd/app-apis`，API 描述文件独立放入 `desc`。
- 业务服务按领域放在 `app/<domain>/rpc`，protobuf 源文件和生成文件放入 `pb`。
- 后台任务放在 `app/pump/cmd/<worker>`。
- 保留独立的 Go 二进制和端口边界，不把多个服务合并为一个进程。
- 使用一个多阶段 Dockerfile 构建五个二进制，并在运行容器内由 Supervisor 负责启动、重启、日志转发和信号传播。
- 容器只对外声明 `app-apis` 的 8888 端口；三个 RPC 端口用于容器内部进程通信。

## 后果

### 正面

- 目录结构能够表达 BFF、业务域和后台任务的职责边界。
- 仍保留 zRPC 接口边界，未来可以无代码迁移到一服务一容器。
- 当前只需构建和部署一个镜像，适合 M1 阶段和单人维护。
- Supervisor 能处理任一子进程异常、标准输出日志和优雅退出。

### 负面

- 任一服务发布都需要重建并重启整个容器。
- 各服务无法独立伸缩，单个进程异常可能造成容器级联重启。
- Supervisor 和多个进程增加了运行镜像体积与容器内运维复杂度。

### 中性

- 服务仍使用独立配置文件和监听端口。
- `report-worker` 在 asynq 接入前保持一个明确记录状态的长运行占位进程。

## 备选方案

**每服务一个容器**

- 故障隔离和伸缩能力最好。
- 当前部署成本过高，暂不采用；服务边界保留后可平滑演进。

**把全部服务合并为一个 Go 进程**

- 镜像更小，也不需要进程管理器。
- 会破坏现有 go-zero 生成入口与服务边界，未来拆分成本高，因此不采用。

**shell 脚本后台启动多个进程**

- 实现简单、运行依赖少。
- 异常重启、僵尸进程回收和退出信号传播不够可靠，因此不采用。
